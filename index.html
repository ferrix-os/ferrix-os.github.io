Ferrix · an operating system written by Claude Code agents

Linux apps without Linux.

A fleet of Claude Code sessions writes Ferrix, a Rust operating system, and a person, the customer, decides what they build. On its own kernel it runs Chrome, rustc, git, Steam and, through Proton, a Windows game. Its disk, network, graphics, input and power drivers run as separate processes that can restart after a crash. Its desktop, Yoru, boots from a live ISO.

Who builds it

Ferrix is not one long chat. It is a team of Claude Code sessions with roles, and one person, the customer, above them. The customer decides scope, priorities and every question of judgement: which game to aim at, how slim the kernel stays, whether a power limit may be raised on real hardware.

A product owner session turns those requests into tasks and starts agents for them. Worker agents each work in a git worktree of their own, build and boot their change in QEMU, and send it to a shared gate pool that runs the tests it needs. A landing lock lets one session at a time move develop, fast-forward only, and main moves only when a promotion from develop passes CI. Quality roles watch CI, flaky tests, documentation drift and performance.

A certification consultant, another Claude session, reviews every change to the kernel's certified core before it lands and asks for a negative control: the check is broken on purpose and must fail. The aim is Common Criteria EAL5+, DO-178C DAL C, IEC 62304 Class C and EN 50716 SIL 2. Nothing is certified, and the review is internal, not independent.

The fleet makes mistakes. Each working rule says which mistake it came from, the roles are written down, and the backlog tracks what is broken.

Yoru, from a live ISO

Yoru is Ferrix's default desktop: a dock, widget sidebars, a launcher and a wallpaper picker on hyprix, Ferrix's own Wayland compositor. The live ISO starts it from memory and touches no disk. Its installer asks for your language, keyboard, disk, account and time zone, and writes nothing until you press Install on the summary page.

New in v0.3.0

Ferrix reads the processor's error banks and survives memory that fails, and the compositor can freeze one program in RAM and thaw it where it stopped. Both pictures are the v0.3.0 live ISO in QEMU.

What the boot tests do

These two commands boot Ferrix in QEMU. One checks that rustc can compile and run a program. The other builds a Ferrix image inside Ferrix and boots that image. The output below comes from their serial logs.

cargo xtask test-rustc

The guest reads the rust-lang.org release of rustc and Debian's glibc from btrfs. Compiling hello.rs calls cc, collect2 and rust-lld, with about 350 MiB of shared libraries mapped from disk. The test then runs the program.

The regular boot test checks the memory map against the loader's allocations, exercises the allocators and checks that four processors can reach exactly 100,000 on a shared counter. It also runs a failing case for each check, to make sure the check catches it.

From Rust kernel to desktop

The kernel

UEFI hands off to a Rust kernel without bootstrap assembly. It runs preemptive tasks on multiple processors, uses an EEVDF scheduler and checks that memory is never both writable and executable.

Linux programs, unchanged

Ferrix implements the Linux system-call ABI used by threads, signals, fork, execve and more, 32-bit x86 programs included. Wine and Proton run Windows programs on it.

Drivers in ring 3

Disk, network, graphics, input, sound and power drivers run as processes, each sealed in a job that only ending leaves. An IOMMU limits their device access on x86-64, Intel and AMD, and on AArch64. A crashed driver restarts; one that keeps crashing backs off, and its device is then quarantined.

A desktop

hyprix, Ferrix's Wayland compositor, reads hyprland.conf and tiles windows, or floats and snaps them, with an overview and title bars. Yoru adds a dock and sidebars. GTK 4 and libadwaita programs run on it, and a program can be frozen in RAM and resumed where it stopped.

Real hardware

An Intel N150 mini PC boots Ferrix from its SATA drive to Yoru, with its own network, USB, GPU and power drivers, and runs Arknights: Endfield from Steam on them. Ferrix has also booted on a Pixel 7's eight cores and an STM32MP157D-DK1 board.

Containers

pid, user, mount, network, UTS, IPC, time and cgroup namespaces, cgroup v2 limits and seccomp filters. A test runs an unprivileged container under a memory limit on all three architectures.

A userland of its own

ferrousli is Ferrix's C library, written in Rust. The zinc shell runs oh-my-zsh, and behaves as sh when started as sh. yserver is its X server in Rust, and tole its UI framework, which Settings and the installer are written in.

When hardware fails

On x86-64 Ferrix logs machine checks, on Intel and AMD, and a bad user page ends that program, not the kernel; tests inject these errors under QEMU. A bad frame stays retired across a reboot, an unstable core is taken out of service, and free memory is tested while the machine idles.

Logs that outlast a crash

lode, a log service in a sealed ring-3 job, collects programs' and drivers' lines and keeps a record of each crash. Read on the next boot, the last boot's log ends with what the machine said before it stopped.

Updates with a way back

A disk can carry two system slots, and a new system that does not come up falls back to the good one. cargo xtask test-ab-boot runs that path.

Developing on Ferrix

The toolchain volume carries cargo, clippy, rust-analyzer and the helix editor, and Ferrix builds its own image. Claude Code runs a full session on its desktop.

On the way to a microkernel

In the fast build, Linux's system calls, btrfs and the network switch run as processes, linuxd, btrfsd and netd, and the kernel keeps only address spaces, memory, channels and scheduling. It runs Linux programs on AArch64 in QEMU; the live ISO keeps the Linux layer in the kernel, and nothing of it is claimed yet.

What this page says about the N150 comes from runs on that one machine, not from a gate. The Intel GPU design says how its driver is built, following Linux's i915 file by file but running as a process.

Try it

Start with the latest release's live ISO: Yoru from memory, with the installer. It needs a 64-bit x86 PC or virtual machine with UEFI, and Secure Boot off. It is a development preview, so do not put anything on it that you cannot lose.

Download the live ISO The Try Ferrix guide →
  • QEMU is the tested machine. Try Ferrix gives the command line. The release was not checked on real PCs, VirtualBox or VMware.
  • Installing needs a disk it can read. Attach the ISO to a virtual machine as a disk. Booted from a CD or a USB stick the live session works, but the installer says it cannot copy the system and writes nothing.
  • Turn on the IOMMU before you install. Without VT-d, AMD-Vi or the virtual machine's IOMMU, the installed system starts no USB, disk or network driver. The live session starts them anyway, unisolated, and says so in its boot log.
  • A PC gets little hardware. The firmware's framebuffer, USB keyboards and mice, no Wi-Fi, and Ethernet only on the YT6801 and some RTL8111/8168 chips. The release notes list the rest.
  • It is the small desktop. The ISO and the zip below carry no Chrome, no Steam and no rustc. Those need a build from source and downloads of their own, which the technical guide covers.

The release's desktop zip is quicker still, and needs only QEMU. To build Ferrix yourself, install Rust and QEMU first; the commands run on Linux, macOS or Windows.

# the released desktop as a zip, no Rust needed (Linux or macOS)
curl -LO https://github.com/ferrix-os/ferrix/releases/latest/download/ferrix-x86_64-desktop.zip
unzip ferrix-x86_64-desktop.zip && sh ferrix-x86_64-desktop/run.sh

# or clone and boot to a shell on the serial console
git clone https://github.com/ferrix-os/ferrix && cd ferrix
cargo xtask run --arch x86_64

# the Wayland desktop with a terminal
cargo xtask run-compositor

# run the project checks
cargo xtask check

Quit QEMU with Ctrl-A x. The install guide covers the zip on Windows and Linux, and the technical guide every flag, Chrome and the Rust toolchain.

FAQ

Who writes the code?

A fleet of Claude Code sessions: a product owner session, worker agents in their own git worktrees, a certification consultant and quality roles. A person, the customer, decides scope, priorities and every question of judgement. The working rules and the tests are in the repository.

Is Ferrix based on Linux?

No. Ferrix has its own Rust kernel, drivers, file systems, C library, shell and compositor. It implements the Linux system-call ABI used by the programs it is tested with, so those binaries run unchanged. uname -s says Ferrix.

Is any of it certified?

No. Certification of the kernel's core is an aim. A certification consultant, itself a Claude session, reviews every change to that core before it lands. That review is internal, not independent, and no outside assessor is involved.

Can I use it every day?

No. Ferrix is an experimental system. It runs a desktop, a browser, a compiler and a game, but most of its tests run in QEMU, it has run on very few PCs and much of it is unfinished.

Can I install it?

In a virtual machine, yes: the live ISO's installer puts Ferrix on a disk of its own, as a development preview. Attach the ISO as a disk and turn on the IOMMU first. Installing on a PC from a USB stick comes in a later release, because Ferrix does not read USB disks as disks yet. Do not put anything on it that you cannot lose. Try Ferrix has the steps.

How can I help?

Try booting it and file an issue if something fails. Human contributions are welcome, and you can follow releases on GitHub.
